PostgreSQL学习笔记

teacupxuan Lv3
  2025-11-04 23:36:31 2025-11-04 23:36:31 创建   2025-11-04 23:36:16 2025-11-04 23:36:16 更新  
  • 技术分享 
 
  • PostgreSQL 
 
  • PostgreSQL像是一个“瑞士军刀”：它功能极其丰富，严格遵守SQL标准，特别擅长处理复杂的数据类型和复杂的查询。
  • MySQL像是一把“锋利的菜刀“：它速度快，简单易用，特别适合处理高并发的读请求，是Web应用的传统首选。

一、PostgreSQL的架构是什么样的？

PostgreSQL的架构核心是多进程模型，而不是很多像其他数据库（包括MySQL的InnoDB引擎）那样的多线程模型。

当你启动一个PostgreSQL服务时，会发生以下事情：

  1. 启动一个”总管“进程：
    • 这个进程时所有PostgreSQL进程的父进程，它负责管理整个数据库实例的生命周期。
    • 它会预先分配一块共享内存，这是PG架构的核心。这块内存里包含了：
      • 共享缓冲区：这是PG最重要的缓存区域，用来缓存从磁盘读取的数据页（表和索引）。客户端的读写操作主要是在这里进行的。
      • 预写日志缓冲区：WAL（Write-Ahead Logging）是保证数据不丢失的关键。任何数据的修改都会现在这里被记录成日志，然后再写入磁盘。
  2. 启动一系列”工人“进程
    • 总管进程还会启动一些常驻的后台”工人”进程，它们各自负责专项任务，比如：
      • WAL写入进程：负责把WAL缓冲区里的日志刷到磁盘上。
      • 后台写入进程：负责把共享缓冲区里被修改过的”脏“数据页在后台慢慢写回磁盘，避免I/O风暴。
      • 检查点进行：定期执行”检查点“，确保所有在某个时间点之前的数据都已安全落盘，这是数据库恢复的关键。
      • 自动清理进程：PG使用一种叫MVCC的技术（下面会讲），这个进程负责自动清理过期的数据版本，回收空间。
  3. 当一个客户端连接过来时：
    • ”总管“进程会fork（派生）出一个全新的、独立的子进程，这个子进程叫做后端进程。
    • 这个后端进程只为这一个客户端连接服务。你应用的所有SQL查询、事务处理，都由这个专属的进程来完成的。
    • 这个进程会使用共享内存来读写数据，同时它也有自己的私有内存，用来做排序、哈希连接等操作。

这个架构的优缺点：

  • 优点（稳定性）：由于每个连接都是一个独立的进程，如果某个连接因为Bug或恶意查询崩溃了，它只会导致自己的那个后端进程死掉，不会影响到其他连接和整个数据库服务。
  • 缺点（连接开销）：如果有一万个并发连接，理论上就要创建一万个进程。这在操作系统层面上的开销（内存、CPU调度）会非常大。因此，在实际应用中，PostgreSQL前面通常会挂一个连接池，比如PgBouncer，来复用连接，解决这个问题。

二、为什么有了MySQL还要有PostgreSQL？

这是一个“萝卜白菜，各有所爱”的问题，但更是“锤子和钳子”的问题。它们被设计出来解决的侧重点不同。

  1. 核心定位不同
    • MySQL（关系型数据库RDBMS）：它的设计目标是快速、简单、可靠。它非常适合结构清晰的表（比如用户表、订单表），并且在Web应用（高并发读）场景下表现极其出色（尤其是在早期的LAMP架构中）。
    • PostgreSQL（对象关系型数据库ORDBMS）：它从设计之初就更“学院派”，目标是功能强大、严格合规、可扩展性强。它不仅支持标准的关系型数据，还支持“对象”特性，比如：
      • 丰富的数据类型：原生支持JSON / JSONB、数组、地理空间数据、键值对等。
      • 强大的扩展性：你可以自定义数据类型、自定义函数、甚至自定义索引类型。
  2. 核心优势对比
特性 PostgreSQL (瑞士军刀) MySQL (锋利菜刀)
数据复杂性 胜出。处理 JSONB、地理位置、数组等非结构化数据非常强。 相对较弱。虽然也支持 JSON，但功能和性能通常不如 PG。
SQL 标准遵从 胜出。非常严格地遵守 SQL 标准，行为一致性高。 相对宽松。有时为了性能或易用性会做一些“妥协”。
并发控制 (MVCC) 非常成熟。PG 的 MVCC 实现被广泛认为是业界标杆，读写不互斥，在高并发写入时表现稳健。 也使用 MVCC (InnoDB)，但在某些高并发读写混合场景下可能不如 PG。
复杂查询 胜出。拥有非常强大的查询优化器，擅长处理复杂的多表连接 (Join)、子查询和分析函数 (Window Functions)。 相对较弱。对于非常复杂的 SQL 语句，优化器可能不如 PG 智能。
简单读性能 良好。 **胜出 (传统强项)**。在简单的“读密集型” Web 应用中，历史表现非常快。
易用性/生态 学习曲线稍陡，配置稍复杂。 **胜出 (传统强项)**。上手简单，文档丰富，是很多初学者的首选。

  1. 场景总结
    选择PostgreSQL的理由：

    • 数据完整性至上：你的应用（比如金融、科学计算）对数据一致性和标准遵从有极高要求。
    • 复杂数据和查询：你需要存储和查询 JSON、地理空间数据、数组，或者你的报表系统有大量复杂的 JOIN 和分析需求。
    • 读写混合高并发：你的应用有大量的并发写入和更新操作，PG 的 MVCC 架构在这种场景下表现非常出色。
    • 强大的扩展性：你需要自己定义数据类型或函数来处理特定业务。

    选择MySQL的理由：

    • 读密集型应用：你的应用主要是读取数据，比如内容管理系统 (CMS)、博客、简单的电商网站。
    • 简单和快速：你需要快速开发和部署，对数据库的复杂功能要求不高。
    • 成熟的生态和运维：你的团队对 MySQL 非常熟悉，有成熟的运维经验和工具链。

总结一下：MySQL 以其速度和易用性赢得了 Web 时代的半壁江山；而 PostgreSQL 则凭借其功能的强大性、数据处理的灵活性和严格的完整性，在今天数据日益复杂的企业级应用和大数据分析领域（OLAP）中，正变得越来越受欢迎。

补充：
LAMP 是一种经典的开源软件组合架构，广泛用于动态网站和Web应用的开发与部署。LAMP 是 Linux、Apache、MySQL 和 PHP/Perl/Python 的缩写，分别代表操作系统、Web服务器、数据库和编程语言。
