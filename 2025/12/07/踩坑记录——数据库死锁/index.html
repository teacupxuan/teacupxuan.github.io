数据库死锁

teacupxuan Lv3
  2025-12-07 22:10:31 2025-12-07 22:10:31 创建   2025-12-07 22:13:39 2025-12-07 22:13:39 更新  
  • 技术分享 
 
  • 数据库 
 

2025年12月1日，我在实习公司上传的代码在真实的线上环境中造成了数据库死锁！死锁把所有的连接都占满了，数据库完全不可用，导致整个微服务全部崩盘，所有接口都报错504。下面是对这个故障的完整复盘！

此次踩坑：后端开发中最经典、也是最容易被忽视的“坑”——资源顺序不一致导致的死锁（AB-BA Deadlock）。

1. 核心复盘：为什么会发生这次死锁？

根本原因就是“加锁顺序不一致”。

  • 事务A的顺序：先锁100，再锁200。
  • 事务B的顺序：先锁200，再锁100。

为什么顺序会不一致？
实例A走了索引扫描，实例B走了顺序扫描，导致返回的顺序不同。这是问题的关键！

资深工程师经验之谈：在SQL标准中，如果没有显示加 ORDER BY，数据库不保证 SELECT 返回结果的顺序。

  • 情况1（索引扫描）：数据库沿着B+树索引叶子节点走，拿到的数据天然是按ID排序的（比如100，200）。
  • 情况2（全表/物理扫描）：数据库直接读磁盘Page，谁存在前面先读谁。如果之前发生了更新、删除导致物理存储位置变动，读出来的顺序完全可能是乱的（比如200，100）。
  • 情况3（并行查询）：PostgreSQL可能会开启并行Worker，多个线程同时读，谁先读完谁先返回，顺序更是随机的。

代码逻辑漏洞在于：你在应用层拿到 List<Team> 后，直接遍历这个List去执行update，而没有在应用层对这个List进行预排序。你是把“锁的顺序”交给了“数据库随机的返回顺序”去决定，这就埋下了地雷。

2. 深度剖析：死锁产生的原理（操作系统视角）

死锁不仅仅是数据库的问题，它是并发控制领域的终极难题。在操作系统（OS）层面，死锁的产生必须同时满足以下四个条件（Coffman Conditions）。只要打破其中任意一个，死锁就不会发生。

死锁的四个必要条件

  1. 互斥条件
    • 解释：资源是独占的。比如数据库的行锁，我锁了，你就不能动这一行。
    • 现状：这是业务必须的，为了数据一致性，我们必须互斥。
  2. 请求与保持条件
    • 解释：吃着碗里的，看着锅里的。我已经拿到了资源A，不释放，同时去申请资源B。
    • 现状：我的死锁就是这样发生的。
  3. 不可剥夺条件
    • 解释：我拿到的锁，除非我自愿释放，否则谁也不能强行抢走。
    • 现状：数据库默认不会强行中断正在正常执行的事务，除非触发死锁检测。
  4. 循环等待条件
    • 解释：A等B，B等A，形成闭环。
    • 现状：就是此次事故的情况。

操作系统中如何避免死锁？

死锁的预防

通过破坏死锁的四个必要条件之一来防止死锁的发生：

  • 破坏循环等待条件：为资源分配编号，进程必须按编号递增的顺序请求资源，避免形成循环等待。

  • 破坏请求与保持条件：要求进程在请求新资源时，必须释放已占有的资源。

  • 破坏不可剥夺条件：允许系统强制剥夺资源，将其分配给其他进程。

这种方法简单直接，但可能导致资源利用率降低。

死锁的避免

通过动态分配资源，确保系统始终处于安全状态。例如：

  • 银行家算法：在分配资源前，系统会模拟分配过程，判断分配后是否仍处于安全状态。如果安全，则分配资源；否则拒绝请求。

银行家算法有效避免死锁，但需要进程提前声明最大资源需求，实际应用中较少使用。

死锁的检测与解除

允许死锁发生，但通过检测和恢复机制解决问题：

  • 检测：系统定期检查资源分配图，寻找是否存在循环等待路径。如果存在，则说明发生了死锁。

  • 解除： 抢占资源：从某些进程中剥夺资源，分配给死锁进程。 终止进程：终止部分或全部死锁进程，释放资源。 进程回退：让进程回到之前的安全状态。

检测与解除方法灵活，但可能带来较高的系统开销。

Linux 的死锁处理

Linux 通常通过以下方式处理死锁：

  • 忽略死锁：在某些情况下，Linux 选择不主动处理死锁（如鸵鸟算法），因为死锁发生概率较低。

  • 死锁检测：通过内核模块或用户态工具（如 _lsof_）检测死锁。

  • 资源抢占：在必要时强制剥夺资源。

Windows 的死锁处理

Windows 提供了更丰富的死锁处理机制：

  • 内核支持：Windows 内核通过资源分配图检测死锁。

  • 调试工具：使用 Windows Debugger 或 Performance Monitor 分析死锁。

  • 优先级调整：通过调整进程优先级，打破循环等待。

无论是 Linux 还是 Windows，死锁的处理都需要在性能与安全性之间权衡，具体策略取决于系统设计和应用场景。

3. 数据库中的死锁与处理

数据库里的死锁是怎么发生的？
数据库（如PostgreSQL，MySQL InnoDB）主要通过锁机制来实现事务隔离。除了本次遇到的这种行锁冲突，数据库里还有更复杂的死锁场景：

  • 间隙锁冲突（常见于MySQL RR 隔离级别）：两个事务同时锁同一个间隙，然后都要在这个间隙里插入数据。
  • 锁升级：虽然现代DB很少锁全表，但在某些特定条件下（如内存不足），行锁可能升级为页锁或表锁，导致预期之外的冲突。
  • 索引覆盖冲突：一个事务通过主键更新，另一个通过二级索引更新，加锁顺序可能是“主键 -> 二级索引” vs “二级索引 -> 主键”，导致死锁。

数据库如何处理死锁?
数据库比操作系统“聪明”一点，它不会像OS那样死机。

  • 死锁检测机制： 数据库内部维护一张图，每当有事务等待锁时，就画一条边。后台有一个线程专门检查这张图有没有环 。
  • 牺牲者选择： 一旦检测到环，数据库会选择一个回滚代价最小（通常是修改行数最少、或者事务启动最晚）的事务进行Rollback，报错给客户端。

4. 解决方案：如何避免死锁？

解决死锁通常由三板斧，特别是针对我的这种业务场景。

方法一：应用层固定顺序（最推荐）
这是解决 AB-BA 死锁的银弹。不管数据库返回顺序如何，你在 Java/Go/Python 代码里，在开始事务之前，强制对要更新的ID列表进行排序。

原理：破坏了”循环等待“条件。如果所有人都按 1，2，3... 的顺序拿锁，就不可能出现环。

方法二：一次性锁定（原子化）
尽量避免在循环里一条条Update。如果业务允许，使用批量更新或批量锁定。

拿到所有锁之后，再去内存里做计算，最后Update。

方法三：缩短事务持有锁的时间

  • 不要在事务中穿插RPC调用（如调用HTTP接口）。
  • 不要在事务中做复杂的非DB计算。
  • 拿到数据后，尽快处理，尽快Commit。

5. 模拟面试：面试官会如何针对这个情况对我进行追问？

如果在简历上写了“解决了生产环境死锁问题”，面试官会抛出连环问，看看到底了解得多深：

追问1：打破死锁的四个条件中，哪一个最容易实现?
参考回答：打破 “循环等待条件” 最容易。因为“互斥”是数据一致性要求的，“不可剥夺”是事务原子性要求的，“请求与保持”是复杂业务流必需的。只有“循环等待”可以通过全局统一加锁顺序（资源有序分配法）来降低成本避免。
追问2：MySQL / PostgreSQL 的死锁检测会影响性能吗?
参考回答：会。死锁检测需要遍历锁图，如果并发事务非常多，锁非常多，这个图会很大，检测环的算法复杂度（DFS）会消耗CPU。
- 进阶点：在高并发场景下，有时候我们会关闭死锁检测（设置超时时间），直接利用 Lock Wait Timeout 让事务超时报错，以此来换取更高的吞吐量（虽然这种比较极端）。

追问3：除了数据库死锁，你在代码层面（Java/Go）遇到过死锁吗？怎么排查?
参考回答：
- 场景：两个线程，锁A和锁B顺序不一致。
- 排查：使用 jstack (Java) 或 pprof (Go)导出线程快照（Thread Dump）。查找状态为 BLOCKED 的线程，通常工具会直接提示 Found one Java-level deadlock 。

追问4：分布式事务下的死锁怎么解？（如果是微服务架构）
参考回答：这就很难用本地数据库的锁检测了。通常需要引入分布式锁并设置超时时间。利用”超时“来作为打破死锁的兜底方案（打破”不剥夺“条件）。
